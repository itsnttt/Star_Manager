# 角色卡库布局

### 人物卡关联物品状态标签靠右（2026-10-18）

- **背景**：人物卡详情“关联”页的物品卡右侧操作列为状态标签预留了固定宽度，“已匹配”等短标签默认贴在该列左侧，视觉上没有与卡片右边缘对齐。
- **解决方案**：仅在人物卡详情关联区域将依赖状态标签设置为网格项末端对齐；缺失、检查中和模组状态沿用相同的右侧定位，下载进度区域和其它卡片类型不变。
- **验证结果**：通过前端生产构建和 `git diff --check` 验证。
- **适用边界**：只影响人物卡详情“关联”页的物品/模组状态标签横向位置，不改变依赖匹配逻辑、状态颜色、操作按钮或服装卡/场景卡布局。

### 人物卡关联物品来源文字显示修正（2026-10-18）

- **背景**：物品已匹配时，右侧状态列仍按下载和缺失状态保留较宽的最小宽度，来源模组文字在窄侧栏中被过度省略。
- **解决方案**：仅对已匹配物品卡将状态操作列收窄到状态标签所需宽度，并继续将标签靠右对齐；来源文字填满中间列的剩余空间后再省略；缺失模组、安装按钮和下载进度继续使用原有操作列宽度。
- **验证结果**：通过前端生产构建和 `git diff --check` 验证。
- **适用边界**：只改善人物卡详情“关联”页已匹配物品的来源文字可见空间，不改变来源数据、状态判断、缺失项布局或其它卡片类型。

### 批量删除人物卡确认弹窗移除重复信息（2026-10-18）

- **背景**：批量删除人物卡确认弹窗中的“将要删除”“所在目录”和“可逆性”三行信息与上方的移入回收站说明及确认按钮重复，占用弹窗空间。
- **解决方案**：移除这三行信息，保留批量删除标题、移入 `runtime/trash/cards` 的说明、错误提示和取消/确认操作；删除范围、回收站处理和按钮状态保持不变。
- **验证结果**：通过 `npm run build` 和 `git diff --check` 验证 Vue 模板及生产构建。
- **适用边界**：仅影响批量人物卡删除确认弹窗的可见文案和高度，不改变单卡删除弹窗、删除任务或回收站恢复/永久删除流程。

### 批量删除人物卡确认按钮文案简化（2026-10-18）

- **背景**：批量删除人物卡确认按钮包含删除数量和卡片类型，按钮宽度较大。
- **解决方案**：将非执行状态的确认按钮文案简化为“确认”；执行中的“删除中...”状态、按钮禁用状态和删除逻辑保持不变。
- **适用边界**：仅影响批量人物卡删除确认按钮的静态文案，不改变选中数量、删除范围或回收站处理。

### 人物卡目录树与列表加载现状（2026-10-15）

- **目录树计数**：`build_character_card_tree()` 从 `character_cards` 索引生成目录计数和 AIS 卡文件签名，并使用 `os.scandir()` 枚举目录。它会把索引签名与当前 PNG 文件名、大小和 `mtime_ns` 对比；签名未变化的目录复用索引计数，变化目录重新检查 AIS marker。根级 `navi` 不计入人物卡目录树。
- **marker 检查**：目录扫描通过 PNG IEND 后的固定 256 字节探测 AIS marker，并用文件大小和 `mtime_ns` 缓存检查结果；不会把整段人物卡尾部载入内存。索引缺失或目录文件集合变化时，相关 PNG 仍需重新确认 marker。
- **前端目录树**：`VirtualCharacterCardTree` 只渲染可视区域前后各 8 行；后端仍返回完整目录树，前端也仍会展平已展开节点，因此虚拟化限制的是树行 DOM 数量，不是目录数据和行模型的总内存。
- **列表加载**：当前目录首屏请求 96 张卡，接近列表底部时按页追加。后端枚举所选目录的直属 PNG，并只为当前页查询 SQLite 浏览元数据；文件签名匹配时复用索引姓名、收藏、评分、标签和依赖计数，签名不匹配时读取卡片列表元数据并更新浏览缓存。完整详情和依赖解析仍在打开单卡时执行。人物卡库无标签模式一次请求完整轻量列表，标签、性别、收藏和依赖状态由前端筛选，不触发分页追加。
- **空根目录与查询范围**：根节点没有直属人物卡时，前端跳过必然为空的根目录列表请求。非根目录列表只按当前页文件路径读取人物卡索引，不读取整张卡片表；目录树的索引加载仍会读取并处理该游戏目录对应的索引记录，并遍历当前目录结构生成签名。
- **诊断信息**：目录树接口返回 `index_load_ms`、`scan_ms`、`count_ms`、`total_ms`、目录数、PNG 候选数、AIS 检查数、计数来源和签名变化目录数；列表接口返回索引读取、文件枚举、卡片处理和总耗时等字段。前端分别以 `[Cards Tree Timing]` 和 `[Cards List Timing]` 记录每次对应响应的统计。
- **验证入口**：实现对应 `apps/backend/star_manager/services/card_library.py`、`apps/backend/star_manager/core/card_parser.py`、`apps/src/components/VirtualCharacterCardTree.vue` 与 `apps/src/App.vue`；当前专项回归覆盖见 `apps/backend/tests/test_card_library_listing.py`。本节描述代码现状，不把旧合成目录或旧游戏目录的毫秒数当作当前机器的性能保证。

## 目标

角色卡库用于浏览所选 HS2 游戏目录中的 AIS 人物卡、服装卡和 Studio 场景卡。该模块在导航中显示为“卡片管理”，侧栏的三个 SVG 类型按钮可互斥切换人物卡、服装卡和场景卡子界面。人物卡、服装卡和场景卡均已接入独立浏览与缩略图接口；服装卡保留完整解析详情，场景卡提供文件详情、场景级依赖解析和目录定位。文档内仍以“角色卡库”描述人物卡业务边界。

## 卡片预览图统一加载规则（长期规则）

人物卡、服装卡以及后续新增的卡片类型，所有列表预览图必须统一采用服装卡浏览器已验证的加载逻辑：

- 列表接口只返回轻量卡片信息和稳定的预览 URL，不为显示缩略图执行完整卡片解析。
- 预览图统一复用后端标准化 `card_previews` 缓存，并以源文件路径、大小、`mtime_ns` 和目标尺寸作为缓存签名；不得在前端直接读取或重复解码原始卡片 PNG。
- 列表网格统一使用 `LazyThumbnail` 的 `IntersectionObserver`，只请求视口附近图片；首屏附近可以设置有限数量的高优先级图片，不能取消整体懒加载。
- 卡片数量可能超过一个视口时，必须使用虚拟网格，只创建视口前后少量行的 DOM；分页数据也不得无限制地同步渲染为完整卡片树。
- 点击卡片后才加载完整详情、依赖和关联信息。详情预览可以按需加载可见 PNG，但仍应优先使用标准化预览缓存；只有明确需要原图时才请求 `original=1`。
- 新增卡片类型或新的卡片列表入口时，必须复用上述缓存、懒加载和虚拟渲染边界，并在本文件和缓存登记中同步记录例外情况。

该规则只约束预览图和列表展示链路，不改变卡片详情的完整解析、依赖匹配、原始文件写回或删除恢复行为。

- 导出过程不覆盖已有文件，文件名冲突时自动增加数字后缀。
- 按当前人物卡生成便携依赖包，将人物卡、已匹配 zipmod、zipmod 引用的游戏目录外部 Unity3D 与依赖清单组织为可直接对应游戏根目录的 `UserData/chara`、`mods`、`abdata` 结构；

- 下载文件统一放入当前游戏目录的 `mods/Remote/`，保留远程索引的相对目录层级。后端先写 `.part` 临时文件并校验文件大小、ZIP CRC 和 manifest GUID，成功后原子改名；下载完成会执行单文件索引并重新读取当前卡片依赖状态。该补全流程同样用于服装卡和场景卡详情页。

#### 便携依赖包性能实测（2026-09-25）

- **背景**：用户反馈单张人物卡生成 ZIP 便携依赖包缓慢。以用户提供的第二张 AIS 人物卡测试；其 SHA-256 与游戏目录 `female/HS2ChaF_20260820002524830_Furuta Yuka.png` 完全一致。
- **根因**：该卡有 20 条依赖，去重后需导出 16 个 zipmod，源文件合计约 864 MB。旧流程先把 zipmod 复制到临时目录，再使用 `zipfile.ZIP_DEFLATED`、`compresslevel=6` 对已经是 ZIP 格式的 zipmod 整包重新压缩。旧流程完整导出耗时 29.1 秒，其中依赖解析约 0.04 秒、文件复制约 0.36 秒、ZIP 写入约 28.6 秒，`zlib` 压缩调用占 27.0 秒。输出约 777 MB。
- **解决方案**：ZIP 输出统一改为 `ZIP_STORED`，只打包人物卡、zipmod、外部 Unity3D 和依赖清单，不再对条目重压缩；文件夹模式、现有路径、依赖筛选和 `compress` 设置字段保持原有契约。界面将“压缩为 ZIP”改为“打包为 ZIP”，任务阶段提示改为“正在打包”。
- **验证结果**：同一张卡运行完整导出耗时 1.97 秒，ZIP 约 868 MB，含 18 个条目（16 个 zipmod、人物卡和清单），全部为 `ZIP_STORED`；清单计数正确，ZIP CRC 校验通过，没有缺失依赖或复制失败。`test_card_library_navi.py` 覆盖 ZIP 条目类型和内容读取。此前同组文件的独立试验中，仅打包耗时 1.24 秒；DEFLATE 1 级耗时 19.3 秒、输出约 771 MB。
- **适用边界**：计时来自本机这一张卡、当前磁盘与 Python 环境，其他卡片依赖体积不同。仅打包使本例 ZIP 比旧流程大约 91 MB；`compress=true` 仍表示输出 ZIP，不能据字段名推断 ZIP 条目经过压缩。试验产物已删除。

### 三类卡片统一依赖状态

人物卡、服装卡和场景卡的关联列表使用同一套降级和补全规则：

场景卡关联列表包含场景级地图、物品、图案，以及场景内嵌 `AIS_Chara` 人物卡的服装、发型、面部、身体和配饰依赖；人物依赖按普通人物卡物品域匹配，Studio 物品仍按场景物品规则匹配。

- 数据库精确找到物品时显示物品级依赖和“已匹配”；
- 找不到物品时按 manifest GUID 合并为模组级依赖；
- 模组未安装且远端索引有有效候选时直接显示安装操作，可单项或全部安装；
- 模组未安装且远端没有有效候选时显示“模组未安装 不可补全”；
- 模组已安装但物品记录缺失时分两行显示“模组存在”和“物品缺失”，这是特殊诊断状态，不进入可补全列表。

模组级条目会保留原始依赖的使用位置和数量，安装后仍以本地数据库的物品级精确匹配结果为准。

模组级降级条目没有可对应的具体物品，因此不渲染物品缩略图或 `MISS` 占位块，也不重复显示 GUID/数量来源文字；条目在类型标签后显示“包含（N）个缺失物品”，布局直接使用模组名称和右侧状态/操作区域。状态徽标作为唯一状态表达，可补全时显示安装按钮，不可补全时不再额外显示重复控件；“模组存在”和“物品缺失”固定分两行显示并居中对齐。

当模组级条目对应的 zipmod 已存在于本地数据库时，点击该条目复用已有的模组定位流程，优先按本地 `zipmod_id` 查询并跳转到模组浏览器，随后选中对应模组；如果数据库中已没有该记录，则回退到缺失依赖提示。

缺失模组依赖统一收纳到“模组依赖缺失”分组；已匹配的 Studio 物品收纳到“工作室物品”分组，Studio 图案和地图收纳到“其它”分组，避免已存在的 Studio 物品被误报为缺失依赖。

### 全部安装按钮分组归属调整（2026-10-13）

- **背景**：关联页签的“全部安装”按钮原先放在依赖总览栏，用户查看“模组依赖缺失”时需要在上方区域寻找批量操作。
- **根因**：批量安装按钮与总览数量使用同一层布局，没有和实际可补全的模组分组建立视觉归属。
- **解决方案**：人物卡、服装卡和场景卡统一将“全部安装”按钮移动到“模组依赖缺失”分组标题右侧；按钮仍只在存在可补全缺失模组时显示，暂停、继续、准备中和批量安装逻辑保持不变。
- **验证结果**：`npm run build` 通过；三类卡片关联页的单项安装、批量任务和分组数量展示保持不变。
- **适用边界**：仅调整关联页签的按钮位置和标题行布局，不改变远端候选查询、下载任务、依赖匹配或安装文件写回。

### 依赖分组数量徽标精简（2026-10-13）

- **背景**：人物卡关联页的分组数量徽标同时显示总数和“缺 N”，与条目状态信息重复，窄侧栏中容易挤压标题和批量操作。
- **根因**：人物卡模板在总数量徽标内额外渲染了 `group.missingCount`，而缺失状态已经由分组名称、条目状态和红色语义样式表达。
- **解决方案**：移除分组数量徽标中的“缺 N”文字，仅保留该分组的条目总数；服装卡和场景卡原有的纯总数显示保持一致。
- **验证结果**：`npm run build` 通过；依赖条目状态和批量安装操作保持不变。
- **适用边界**：仅调整关联页分组标题的数量徽标文字，不改变缺失依赖统计、远端补全判断或条目列表。

### 补全下载性能排查记录（2026-08-21）

- 背景：补全任务原先逐个下载远程 zipmod；每个文件都要等待网络传输、落盘、ZIP CRC 校验和单文件索引完成后才开始下一个文件。
- 根因：基准测试选取远程索引中 3 个约 10 MB 的真实候选。原顺序路径一次耗时约 70.0 秒，单文件有效吞吐约 `0.31–0.81 MB/s`；同一批文件允许 3 路并行后耗时约 6.9 秒，说明主要瓶颈在远程连接等待和单连接吞吐，SQLite 单文件索引不是该样本的主瓶颈（约 0.06 秒/文件）。公网速度会随站点和时段波动，以上数据用于比较路径而非承诺固定网速。
- 方案：使用固定上限 3 的下载线程池；每个下载仍保留 `.part`、Content-Length 校验、ZIP CRC 校验、manifest GUID 校验和原子安装。所有下载完成后，再按选中顺序执行单文件索引和人物卡依赖刷新；SQLite 写入仍不并行化。任务状态新增 `phase`、`phase_progress`、`download_speed_bps`、字节统计和当前文件字段，前端据此分别绘制两个阶段。
- 验证：`apps/backend/tests/test_remote_mod_completion.py` 覆盖 3 路并发启动、坏包清理、manifest GUID 校验和已有文件重建索引；阶段回调验证下载阶段先于安装阶段，下载速度与字节统计字段按任务进度传递，前端下载阶段显示累计已下载数据量。
- 适用边界：并发仅用于远程文件下载；安装阶段保持单文件顺序，暂停/继续、失败清理和任务协议仍然有效。批量很大时线程数固定为 3，以免对远程站点和本地磁盘造成突发压力；网络速度仅反映当前下载窗口，公网限速会造成波动。

### 下载取消按钮与任务取消记录（2026-08-21）

- 背景：下载任务开始后，依赖卡片操作区仍可能保留“检查中”语义，用户无法从该位置直接终止当前下载。
- 根因：前端任务状态虽然已经关联到依赖卡片，但操作区没有把活动任务优先映射为取消动作；后端也需要等待下载线程在安全检查点结束，不能只在界面隐藏任务。
- 方案：活动下载任务优先显示“取消下载”，调用 `/tasks/:task_id/control` 的 `cancel` action；后端将任务置为 `cancelled`，下载线程抛出取消异常并清理未完成 `.part` 文件，已经原子安装的文件不回滚。取消确认前按钮继续保留，避免用户误以为任务已立即结束。
- 验证：`test_bridge_card_dependency_refresh.py` 覆盖取消请求标记和终态转换，`test_remote_mod_completion.py` 覆盖写入中取消后的临时文件清理；完整后端测试和 `npm run build` 均通过。
- 适用边界：取消只作用于当前远程模组下载任务；网络读取正在阻塞时会等待读取返回或下一次控制检查点，已完成并通过原子替换的文件不会被删除。

人物卡详情工具字体统一（2026-10-18）：

- **问题背景**：工具卡标题、普通操作按钮和 `navi / sitri` 等紧凑按钮的字体族、字号和字重不一致。
- **根因**：普通按钮使用主字体，紧凑按钮单独覆盖为等宽字体 `var(--mono)` 和更小字号，标题又沿用浏览器默认粗体。
- **解决方案**：工具卡内所有标题、按钮和状态文字统一使用 `var(--font)`、`11px` 和 `800` 字重；保留按钮颜色和高度差异。
- **验证结果**：通过前端生产构建和 `git diff --check` 验证。
- **适用边界**：只影响人物卡详情“工具”页签的字体样式，不改变工具操作、颜色、布局或其它详情页签。

人物卡详情导航页签复用模组详情样式（2026-10-18）：

- **问题背景**：人物卡详情的“详情 / 关联 / 工具”页签使用三个连续玻璃按钮，与模组详情页的轻量胶囊导航不一致。
- **根因**：人物卡页签存在独立的网格布局、边框和每个按钮的玻璃底色规则，未复用模组详情的居中导航样式。
- **解决方案**：将人物卡详情页签改为居中横向排列、无边框透明底；非当前页签仅在悬停/聚焦时显示浅色底，当前页签显示白色胶囊背景和阴影，保持“详情 / 关联 / 工具”交互不变。
- **验证结果**：通过前端生产构建和 `git diff --check` 验证。
- **适用边界**：只影响人物卡详情页签导航，不改变人物卡详情内容、工具操作或模组/服装/场景页面页签。

目录树接口返回：

- 节点 ID。
- 节点名称。
- 相对路径。
- AIS 人物卡数量。
- 是否有子节点。
- 子节点列表。
- `is_valid_game_dir`、`root`、`total`。

列表接口当前支持：

- 默认按目录查询，只返回当前目录直属 AIS PNG，不递归包含子目录；普通目录首屏由 renderer 请求 96 张，滚动时追加下一页。
- `scope=library` 时递归返回 `UserData/chara` 下的人物卡并排除根级 `navi`；renderer 无标签请求一次返回完整轻量列表，标签筛选在前端完成。接口仍保留可选 `tag` 参数和 `offset/limit` 兼容调用。
- 返回 `total`、`has_more` 以及 `index_load_ms`、`enumerate_ms`、`card_loop_ms`、`total_ms` 等 timing 字段；完整卡片解析由详情接口按需执行。
- 按文件名排序。
- 返回标准化网格预览 URL 和原始封面 URL。

人物卡列表项建议字段：

- `id`。
- `filename`。
- `name`，可为空。
- `relative_path`。
- `absolute_path`。
- `thumbnail_url` 或缩略图读取标识。
- `cover_url`：详情使用的原始可见 PNG URL。
- `modified_at`。
- `dependency_status`。
- `selected` 仅作为前端状态，不由后端持久化。

当前预览缓存规则：

- 人物卡和服装卡网格优先使用标准化到 `252 x 352` 的 PNG 预览缓存，缓存到 `backend/runtime/card_previews`，避免一次解码大量高分辨率封面。
- 人物卡详情使用原始封面模式，后端只返回人物卡 IEND 之前的可见 PNG，不返回附加人物数据，也不经过预览缓存缩放。
- 如果 Pillow 不可用，则回退到原始卡片文件。
- `/library/cards/image` 只允许读取卡片根目录或预览缓存目录下的文件。

### 缺失数量一致性

- 卡片网格左上角的“缺 N”来自人物卡数据库中的派生缺失模组计数；同一模组缺少多个物品时只计作一个模组。详情栏的依赖状态以当前卡片和当前模组索引实时解析结果为准。
- 补全模组或单独索引 zipmod 完成后，任务会把受影响的模组 GUID 传给人物卡数据库，只增量重连依赖这些 GUID 的卡片；不需要修改人物卡 PNG，也不会扫描无关卡片。
- 详情读取完成后，前端立即用详情结果刷新当前卡片的 `dependencyCount`、物品级 `missingCount` 和模组级 `missingModCount`，避免旧缓存让已匹配卡片继续显示缺失徽章。
- 后端同时用实时解析结果回写该卡的依赖关联表和派生计数；列表接口额外按未解析依赖的唯一 ModID 返回 `missing_mod_count`。这样重新加载卡片目录时不会恢复旧的物品级“缺 N”显示；数据库任务占用 SQLite 时，回写失败不影响详情展示，下一次人物卡扫描仍可重建缓存。
- 该修复只校正显示所依赖的派生索引，不修改人物卡 PNG 内容；对于历史上尚未经过人物卡扫描或受影响 GUID 重连的缓存，仍可通过人物卡扫描刷新全库派生索引。
